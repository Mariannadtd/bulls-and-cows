# Как устроена игра

Здесь коротко записала, почему проект устроен именно так и какие структуры данных я использовала.

## Данные игры

Секрет храню строкой, а не числом. Это важно для вариантов вроде `0123`: если сделать его числом, первый ноль потеряется.

Одна попытка — это объект `GuessHistoryEntry`, в котором есть введённое значение, быки и коровы. Все попытки лежат в массиве `guessHistory`. Новую запись добавляю так:

```ts
guessHistory = [...guessHistory, newEntry];
```

То есть старый массив не меняется, вместо него создаётся новый.

Рекорды устроены похожим образом. В `GameRecord` сохраняются система счисления, длина секрета, попытки, время и дата. Функция `addRecord` сортирует результаты сначала по количеству попыток, потом по времени и оставляет десять лучших. После этого массив записывается в `localStorage`.

## Основные функции

### `generateSecret`

Функция находится в `src/core/generateSecret.ts`. Сначала она получает набор разрешённых символов для выбранной системы счисления. Потом случайно берёт один символ и создаёт новый массив уже без него. Поэтому одна и та же цифра не может попасть в секрет два раза.

`random` передаётся отдельным аргументом. В самой игре используется `Math.random`, а в тестах я могу передать функцию, которая всегда возвращает известное значение, и получить предсказуемый результат.

### `evaluateGuess`

В `src/core/evaluateGuess.ts` секрет и попытка сначала приводятся к нижнему регистру. Это нужно для hex, чтобы `A` и `a` считались одной цифрой.

Дальше создаётся `Set` из цифр секрета, а `reduce` проходит по попытке. Если совпали и цифра, и индекс — добавляется бык. Если цифра есть в секрете, но индекс другой — добавляется корова. Счётчики напрямую не изменяются, на каждом шаге возвращается новый объект.

### `isValidGuess` и `createDigitValidator`

`createDigitValidator(base)` создаёт проверку для конкретной системы счисления. Например, для binary она пропускает только `0` и `1`, а для hex ещё и `a-f`.

Эта проверка используется в двух местах: внутри `isValidGuess` и прямо в поле ввода. `isValidGuess` дополнительно проверяет длину и повторы цифр. Для поиска повторов использую `Set`.

### `countPossibleSecrets`

Количество возможных секретов считается рекурсивно:

```text
P(base, 0) = 1
P(base, length) = base × P(base - 1, length - 1)
```

Например, для decimal и длины 4 получается `10 × 9 × 8 × 7 = 5040`.

Результаты сохраняются в `Map`. Ключ выглядит как `length:base`, например `4:10`. Если такая комбинация уже считалась, функция сразу возвращает сохранённое значение. Это и есть мемоизация.

## Сложность

- `generateSecret` — **O(length × base)** по времени. После каждого выбора фильтруется оставшийся набор цифр. По памяти получается **O(base + length)**.
- `evaluateGuess` — **O(n)** по времени и **O(n)** по памяти, где `n` — длина секрета. Один проход нужен для `Set`, ещё один — для `reduce`.
- `isValidGuess` — **O(n × base)** по времени и **O(n + base)** по памяти. Для каждой цифры проверяется, входит ли она в разрешённый набор. В проекте `base` не больше 16, поэтому разница практически незаметна.
- `countPossibleSecrets` — **O(length)** при первом вычислении. Столько же занимает стек рекурсии. Если ответ уже есть в кеше, повторный вызов работает примерно за **O(1)**.

## Что из Clean Code использовано

- Игровая логика лежит в `src/core` и не зависит от DOM. Интерфейс вынесен в `src/ui`, поэтому функции ядра можно тестировать без браузера.
- Старалась давать переменным названия по смыслу: `availableDigits`, `normalizedGuess`, `cachedResult`, `updateAvailableLengths`.
- Большие действия разделены на небольшие функции: отдельно валидация, генерация секрета, сравнение, сортировка рекордов и форматирование времени.
- В `handleGuess` и `isValidGuess` использованы ранние возвраты. Если попытка неправильная или уже встречалась, функция заканчивается сразу.
- История и рекорды обновляются без `push`, через создание нового массива.
- В `generateSecret` источник случайности передаётся снаружи. Благодаря этому функцию можно нормально протестировать.

## Тесты

Для тестов использован Vitest. Обязательные функции делались по TDD: сначала отдельный коммит с падающими тестами, потом коммит с реализацией. В тестах нет настоящей случайности, поэтому результат повторяется при каждом запуске.
